What keeps five separately-built packages consistent

A walkthrough of the ratified architecture spine. Every rule on the following slides is quoted verbatim from ARCHITECTURE-SPINE.md — nothing here is new.

The paradigm

Layered, with ports and adapters. Contracts are the ports, every implementation sits behind them, and exactly one layer wires them together.

The ASP.NET Core middleware pipeline is one filter inside that model, not the organising idea. What stays consistent across the family is the contract surface, not the pipeline.

The one test that decides what belongs here

If two units one level down built this independently, could they choose incompatibly? Fix it in the spine only when the answer is yes, and the call is non-obvious, and it is a real trade-off. Otherwise it is named under Deferred.

19 decisions passed that test; 12 items did not and are listed by name.

The shape of the thing

SafeWebCore

Contracts, adapters, middleware, composition root, presets, tag helpers. The only package with symbols and SourceLink today.

FraudDetection

Detectors, option groups, dispatchers, sinks, metrics. Never references SafeWebCore.

JwtBearer

Authority guard, hardening, logging configuration manager. Never references SafeWebCore.

Analyzers

SWC001–SWC004, netstandard2.0, build-time only. Nothing in the family depends on it.

Testing

Header and nonce assertions, test host bootstrap. The one allowed reference: to SafeWebCore.

Verified 2026-09-27

Build green with 25 warnings / 0 errors; 168 tests passed in 2.3 s; zero project references between the four libraries.

The paradigm, layer by layer

Read the arrows as "may depend on". The direction is fixed so a contract never learns about an implementation.

A new type lands in the layer that owns its concern. Infrastructure types never appear in a public signature, and the pipeline never reaches into detector internals.

Watch for

  • A registration appearing outside Extensions breaks the single composition root.
  • A contract reaching for an adapter is the direction reversing.
  • Anything depending on SafeWebCore.Analyzers is wrong by definition.

Package boundaries

Five packages, no sideways coupling. The red badges are the references that may never exist.

AD-1 — Packages are independent siblings

No ProjectReference and no PackageReference from one SafeWebCore.* package to another. One exception: SafeWebCore.Testing to SafeWebCore. Shared behaviour is promoted into SafeWebCore as public API or duplicated deliberately, never referenced sideways.

Evidence: zero project references between the four libraries, verified 2026-09-27.

AD-2 — One-way dependency direction, single composition root

Contracts depend on nothing else in their package; adapters and the pipeline may depend on contracts and on adapters; only Extensions composes. Nothing in the family depends on SafeWebCore.Analyzers.

Both rules are review-enforced today. An architecture test for layer direction and sideways references is on the deferred list.

The 19 decisions

Rule text quoted verbatim from the spine. Filter by the package you are touching.

AD-1 Packages are independent siblings

Binds: all five packages under src/
no ProjectReference and no PackageReference from one SafeWebCore.* package to another. One exception: SafeWebCore.Testing to SafeWebCore. Shared behaviour is promoted into SafeWebCore as public API or duplicated deliberately, never referenced sideways.

AD-2 One-way dependency direction, single composition root

Binds: all packages
contracts depend on nothing else in their package; adapters and the pipeline may depend on contracts and on adapters; only Extensions composes. Nothing in the family depends on SafeWebCore.Analyzers.

AD-3 Additive-only public API, enforced by the PublicAPI baseline

Binds: SafeWebCore, SafeWebCore.FraudDetection, SafeWebCore.JwtBearer
never remove or rename a symbol listed in PublicAPI.Shipped.txt; add intentional new public API to PublicAPI.Unshipped.txt in the same change; keep XML documentation on all public API; fix RS0037 rather than suppressing it; a breaking change is a deliberate major-version decision, never incidental. SafeWebCore.Analyzers and SafeWebCore.Testing carry no baseline.
Evidence: WarningsAsErrors: RS0037 and WarningsNotAsErrors: RS0016;RS0017 in the three csproj files, plus the backward-compatibility policy.

AD-4 Misconfiguration fails at startup with an actionable message

Binds: SafeWebCore, SafeWebCore.FraudDetection, SafeWebCore.JwtBearer
every option group has an IValidateOptions<T> implementation and is registered with .ValidateOnStart(); each failure message names its scope (global or the specific path policy) and ends with an explicit Fix:; the request path never throws for configuration problems and never silently coerces a value.

AD-5 Per-request state lives only in HttpContext.Items

Binds: all runtime packages
no AddScoped registrations. The per-request nonce is HttpContext.Items[NetSecureHeaders.CspNonceKey], reached through a typed HttpContext extension. New per-request state adds its own constant key plus an accessor extension and is set before await next(context); a key belongs to the type that owns the feature, its string is unique across the family, and callers reach it only through that type's typed accessor. Singleton services hold configuration and stateless helpers, never request state.
Evidence: zero scoped registrations in src/; HttpContextExtensions.GetCspNonce.

AD-6 Options-derived values are materialized once

Binds: SafeWebCore middleware
every header value derived from options is computed in the middleware constructor, for the global options and for each path policy, and is immutable afterwards. The only per-request mutation is Replace("{nonce}", nonce, StringComparison.Ordinal). Nothing in InvokeAsync rebuilds a value from the options object.
Evidence: _defaultCspTemplate, BuildReportingEndpointsValue and BuildPathPolicies all run in the constructor.

AD-7 Exactly one header-emission table

Binds: SafeWebCore
NetSecureHeadersMiddleware.AddSecurityHeaders is the only place that writes security headers to a response; the only other per-response mutation is the removal of Server and X-Powered-By on OnStarting when the options ask for it. Names come from HeaderNames, built-ins go through AddIfEnabled(enabled, name, value), and no raw header-name literal appears at an emission site. A header is library-owned once a HeaderNames constant exists and AddIfEnabled emits it, and AdditionalHeaders must not use a library-owned name, because it assigns through the header indexer and would replace the emitted value. CSP enforcement versus report-only resolves per endpoint (CspModeAttribute, then UseCspReportOnly). Reporting stays a contract: Csp.ReportTo must name a group that exists in ReportingEndpoints, and the sink path remains the documented /csp-report endpoint. CustomPolicies (IHeaderPolicy) run last and are the documented override.
Evidence: AddSecurityHeaders; NetSecureHeadersDiagnosticsService is the preview projection of the same table, not a second emitter; analyzer rules SWC003 and SWC004.

AD-8 A new first-class header follows one seven-step path

Binds: SafeWebCore, and SafeWebCore.Analyzers where the mistake is statically detectable
(1) a typed option or option group with a safe default; (2) a constant in HeaderNames; (3) one AddIfEnabled line in AddSecurityHeaders; (4) inclusion in the relevant SecurePresets set; (5) the matching AddStandardHeader line in the NetSecureHeadersDiagnosticsService projection, so the preview cannot drift from what is emitted; (6) the public symbols recorded in PublicAPI.Unshipped.txt; (7) the feature documented in docs/ with a CHANGELOG.md entry. Add an analyzer rule when a misuse is detectable at build time.

AD-9 Path policies inherit, override explicitly, and the longest prefix wins

Binds: SafeWebCore options
a path policy is created with options.PathPolicy("/prefix", customize), which starts from a clone of the global options, so only explicitly configured values differ. Prefixes normalize to a leading /, compare case-insensitively, and the longest matching prefix wins. Duplicate prefixes after normalization fail at startup.
Evidence: NetSecureHeadersOptionsExtensions.PathPolicy, the descending prefix sort in BuildPathPolicies, and the duplicate check in the validator.

AD-10 Telemetry never blocks the response and never fails the request amended · implemented 2026-09-27

Binds: SafeWebCore, SafeWebCore.FraudDetection
events go to every registered sink through a dispatcher, are awaited fire-and-forget with the request's CancellationToken, and are never awaited inline on the response path. A sink is added with AddSafeWebCoreSecurityEventSink<T> or AddFraudEventSink<T> so the default sinks stay registered. Both dispatchers isolate a throwing sink deliberately: each materializes its sink sequence once in its constructor and invokes every sink inside its own try, because fire-and-forget protects the response, not delivery. A swallowed failure is counted in that dispatcher's metrics type, never silent. When touching either one, keep the request path free of sink exceptions. Delivery order is registration order and therefore deterministic, but nothing may depend on it and no sink may assume another has already run.
All three security-event call sites discard the returned task (_ = _eventDispatcher.EmitAsync(...)), which is why the isolation has to live inside the dispatcher. FraudEventDispatcher already isolated per sink; both now count the swallowed failure — safewebcore.security_event_sink_failures_total and safewebcore.fraud_event_sink_failures_total — and each suite has a test with a throwing first sink.

AD-11 The environment downgrade is opt-in per registration call

Binds: SafeWebCore registration overloads
CSP becomes report-only outside Production only through AddNetSecureHeadersForEnvironment and AddNetSecureHeadersStrictAPlusForEnvironment. The plain registration and preset overloads keep the configured mode in every environment. Changing this is an explicit, documented decision; analyzer rule SWC002 exists to flag report-only that is left on permanently.
Evidence: ApplyEnvironmentRolloutDefaults is called from exactly those two overloads and nowhere else.

AD-12 Fraud detectors are synchronous, side-effect-free and tenant-aware

Binds: SafeWebCore.FraudDetection
IFraudDetector.Analyze(ClientFingerprintData) stays synchronous and returns a FraudReport. A detector may consult the injected IGeoIpService, through the shared GeoIpEnricher, and nothing else: no notifications, no mail or HTTP calls, no persistence. Enriching the fingerprint before the call remains the recommended path the library documents. Tenant options are read per analysis through IFraudDetectionOptionsResolver, where a registered IFraudDetectionConfigurationStore takes precedence over the options monitor. Anything time-dependent uses TimeProvider.

AD-13 The verdict-to-risk mapping lives in exactly one place

Binds: SafeWebCore.FraudDetection
RiskScore.FromScoreAndVerdict is the only verdict-to-level mapping (RegionImpersonation to Critical, HighlySuspicious to High, Suspicious to Medium, everything else to Low) and the only place the score is clamped to 0–100. Every detector populates Risk through it, and RiskScore.None means that no assessment happened, never that the risk is low. Risk stays additive to Verdict and SuspicionScore, and trigger keys are constants in FraudTrigger.

AD-14 JwtBearer hardening runs through the options pipeline

Binds: SafeWebCore.JwtBearer
hardening is applied with Configure<JwtBearerOptions>(scheme, ...) plus a post-configure step, never by editing a resolved options instance. The startup authority guard is registered once (guarded by an existing-descriptor check) as both singleton and hosted service. FailFast = true is the secure default and only an explicit later registration may opt out. A step added to that pipeline later may add hardening; weakening an applied rule is allowed only through an explicit option on the hardening options type, because post-configure steps run in registration order and the guard cannot detect a weakened rule. Helpers that must stay internal use InternalsVisibleTo for the matching test project only.

AD-15 Analyzer rules are warnings, numbered, and documented one by one

Binds: SafeWebCore.Analyzers
every rule is DiagnosticSeverity.Warning with isEnabledByDefault: true, category SafeWebCore, and an ascending SWC0nn id declared only in DiagnosticDescriptors. Each rule gets its own section in src/SafeWebCore.Analyzers/README.md and an entry in AnalyzerReleases.Unshipped.md. Rules never change runtime behaviour and never reference runtime package internals.

AD-16 Enum members are append-only and every verdict mapping fails closed implemented 2026-09-27

Binds: SafeWebCore.FraudDetection
members of FraudVerdict, RiskLevel and RecommendedAction are append-only: a new member is added last, never inserted, reordered or renumbered, and it pins its value explicitly the way RiskLevel does (Low = 0 through Critical = 3, plus the appended fail-closed Unclassified = 4). An unrecognized verdict never maps to the lowest level or to NoAction: RiskScore.FromScoreAndVerdict and every verdict-to-action switch fail closed, so unknown is never reported as safe. One change adds a new member with every arm and the metric tag, and a mapping two detectors need lives in one shared helper.
Was: RiskScore.FromScoreAndVerdict fell through _ => RiskLevel.Low, and DetermineAction was duplicated verbatim in GeoCulturalConsistencyDetector and WesternImpersonationDetector with _ => RecommendedAction.NoAction. Both now fail closed (Unclassified / BlockRequest) through the shared FraudVerdictMapping helper. MaxSeverity compares ordinals and the risk_level tag carries the RiskLevel name, which is why the appended member pins its value. Precedent kept: FakeWestern is [Obsolete] and equals RegionImpersonation rather than freeing a number.

AD-17 Three-part SemVer is the canonical version form implemented 2026-09-27

Binds: the csproj file of each of the five packages and the release documentation
<Version> is three-part SemVer — 1.2.3, optionally with a -preview.N suffix. The four-part form is not used, and the four-part assembly identity is still produced automatically. SafeWebCore.FraudDetection carries 1.1.0 for its next release, and docs/nuget-packages.md states the canonical form and the published versions.
Why: NuGet normalizes 1.0.0.0 to 1.0.0, and FraudDetection 1.0.0 was already published — so the four-part value that csproj carried could never have been pushed again.

AD-18 AdditionalHeaders may not name a header the library owns implemented 2026-09-27

Binds: SafeWebCore options and the options validator
AdditionalHeaders may only name headers the library does not own. An entry whose name matches a header the middleware emits through its typed options — the AddIfEnabled set plus CSP, NEL and Reporting-Endpoints — fails at startup, in the validator, with the options scope and a Fix: naming CustomPolicies / IHeaderPolicy as the supported replacement path. The response header indexer stays the documented override for headers the library does not own, and the check is implemented once, in the validator.
Evidence: the validator rejects duplicates only inside AdditionalHeaders, and emission assigns headers[name] = value after the standard headers and the CSP value, which replaces the emitted value.

AD-19 The root namespace is for the types a consumer names

Binds: SafeWebCore public API layout
a public type a consumer writes by name — in registration, in markup or in an option lambda — lives in the root SafeWebCore namespace (NetSecureHeaders, INonceService); the folder that holds the file is organisation, not the namespace contract. Types grouped by the concern they serve live in the namespace named after that concern. NonceService and INonceService stay root-namespaced inside Infrastructure/; moving them is a major-version change and is not worth one.
Evidence: Infrastructure/NonceService.cs and Infrastructure/INonceService.cs declare namespace SafeWebCore; HttpContextExtensions follows the other half of the rule in SafeWebCore.Extensions.

Runbook: adding a first-class header

AD-8 fixes one path so two units cannot split the configuration surface between a typed option and a stringly-typed AdditionalHeaders entry.

  1. A typed option or option group with a safe default so a preset can turn it on and a consumer can still override it
  2. A constant in HeaderNames no raw header-name literal may appear at an emission site
  3. One AddIfEnabled line in AddSecurityHeaders the single emission table (AD-7)
  4. Inclusion in the relevant SecurePresets set otherwise the preset silently omits the new header
  5. The matching AddStandardHeader line in the NetSecureHeadersDiagnosticsService projection so the preview cannot drift from what is emitted — the step the reviewer gate added
  6. The public symbols recorded in PublicAPI.Unshipped.txt unrecorded public surface blocks a release review (AD-3)
  7. The feature documented in docs/ with a CHANGELOG.md entry plus an analyzer rule when the misuse is detectable at build time
Steps 3 and 5 are the two tables. Skipping 5 is exactly the drift the gate found: the diagnostics preview would advertise a header the response never carries. An automated lockstep check is deferred.

Five questions, decided

The spine left these open on purpose; all five were decided on 2026-09-27 and are folded in as AD-16 to AD-19 plus an amended AD-10. Click a question for the evidence behind the call.

1. Should SecurityEventDispatcher swallow a throwing sink per sink, as FraudEventDispatcher does?

decided folded into AD-10, which was amended.

What the code does today. EmitAsync awaits each sink in a bare loop with no try, and all three call sites discard the returned task (_ = _eventDispatcher.EmitAsync(...)). So one sink that throws ends delivery for every sink registered after it, silently: the response is safe, the remaining events are gone, and the exception surfaces only as an unobserved task exception. FraudEventDispatcher does the opposite — it materializes the sinks into an array once in its constructor and catches per sink.

Decided: adopt the fraud policy. Catch per sink in EmitAsync and materialize the sink list once in the constructor, since the dispatcher is a singleton enumerating a DI-provided sequence on every event. Keep the async signature and the fire-and-forget contract unchanged, and count swallowed failures in SafeWebCoreMetrics so a broken sink is visible instead of silent.

Why not keep it as it is. "Fire-and-forget is the only protection" protects the response, not delivery. A throwing sink is already a bug; letting it also mute every later sink is an accidental trade-off rather than a designed one. Delivery order is already contractual as registration order (AD-10), which only means something if the loop finishes.

Cost. A behaviour change with no API surface change, so no PublicAPI entry; it needs a test with a throwing first sink. AD-10's sentence "the security dispatcher does not catch" has collapsed into one policy for both dispatchers.

2. Is adding a FraudVerdict or RiskLevel member additive, or breaking?

decided folded into AD-16. implemented 2026-09-27

Binary compatibility: additive. Source compatibility: a consumer switching exhaustively on the enum without a default arm stops compiling — a loud, correct failure that AD-3's additive-only rule should name explicitly rather than imply.

The hazard is inside this package, and it fails open. RiskScore.FromScoreAndVerdict maps everything unrecognized to RiskLevel.Low, and DetermineAction — duplicated verbatim in GeoCulturalConsistencyDetector and WesternImpersonationDetector — maps it to RecommendedAction.NoAction. A new severe verdict therefore lands as low risk, no action unless someone remembers every arm, in two files. Both enums are also consumed ordinally: MaxSeverity is (RecommendedAction)Math.Max((int)first, (int)second), and the risk_level metric tag is the RiskLevel name — so inserting or renumbering a member in either enum silently changes ordering or tag values.

Decided. (a) Append-only: new members go last with an explicit value, never renumbered. (b) Fail closed, and the sharper reading won: an explicit, appended Unclassified level, because mapping an unrecognized verdict to Critical would have fabricated a real classification in the risk_level tag and in consumer alerts. (c) One change must add the RiskLevel arm, both RecommendedAction arms and the metrics tag together — the action mapping moved into one shared FraudVerdictMapping helper, so there is only one place left to extend. This belongs in the backward-compatibility policy too. It is AD-16.

Precedent in the codebase. FakeWestern = RegionImpersonation with [Obsolete] is already how a verdict name is retired here — duplicate the value, never renumber.

3. Which version form is canonical: 1.0.0, or the four-part 1.0.0.0?

decided folded into AD-17. implemented 2026-09-27

Where the family stands. Before the release prep the csproj carried SafeWebCore 1.7.0, JwtBearer 1.0.0, Analyzers and Testing 1.0.0-preview.1, and FraudDetection 1.0.0.0. nuget.org already carries all five, including FraudDetection 1.0.0. After the prep it carries SafeWebCore 1.8.0 and FraudDetection 1.1.0.

Why the four-part form was a live trap. NuGet normalizes 1.0.0.0 to 1.0.0, and that version is published — so the <Version> value the csproj carried could never have been pushed again. The next FraudDetection release had to be a higher version regardless of which form was chosen.

Decided: three-part SemVer is canonical (1.2.3, optionally with a -preview.N suffix). It matches the other three packages, it is what NuGet stores after normalization anyway, and the four-part assembly identity is still produced automatically. FraudDetection now carries 1.1.0 for its next release, and the rule is recorded in the release documentation.

Second-order effect to check. Because all five packages are live, any pipeline or documentation step that assumes a first publish (or that read docs/nuget-packages.md, which reported the opposite) had to be corrected first — and it was, on 2026-09-27.

4. Should AdditionalHeaders be prevented from naming a header the library already emits?

decided folded into AD-18. implemented 2026-09-27

Verified behaviour. The validator rejects duplicates only inside AdditionalHeaders (case-insensitively). Emission appends the standard headers and the CSP value and then assigns each additional header through the response header indexer, which replaces the values already there. An entry named Content-Security-Policy therefore discards the per-request nonce substitution — and with it, every nonce-based script or style the app emits. CustomPolicies runs after it and remains the last word.

Decided: guard the library-owned names. Reject, at startup, an AdditionalHeaders entry whose name matches a header the middleware emits through its typed options, with the scope and a Fix: as AD-4 requires — the AddIfEnabled set plus CSP, NEL and Reporting-Endpoints, because the CSP case is the one that costs a nonce. Keep the indexer as the documented override for headers the library does not own, and keep CustomPolicies as the deliberate escape hatch for replacing a library-owned one. Implement the guard once, in the validator — not in both the middleware and the diagnostics projection.

Trade-off. It removes an undocumented way to hand-replace HSTS or CSP by configuration; the explicit IHeaderPolicy path covers that need with a type, which is the point of AD-7.

5. Do NonceService and NetSecureHeaders belong in the root SafeWebCore namespace?

decided folded into AD-19, which changes no code.

What is actually there. Infrastructure/NonceService.cs and Infrastructure/INonceService.cs declare namespace SafeWebCore — the root — while every other type in that folder declares SafeWebCore.Infrastructure. NetSecureHeaders.cs (holding CspNonceKey) sits at the project root and is root-namespaced, and the consistency conventions already say folders mirror namespaces.

Decided: keep it, and the rule is now written down as AD-19. Types a consumer names directly — in registration or in markup — live in the root namespace (NetSecureHeaders, INonceService); the folder is organisation, not the namespace contract. HttpContextExtensions follows the other half of the same logic: SafeWebCore.Extensions, a namespace named after its concern. Moving the two Infrastructure outliers is a source-breaking change for zero functional gain, which makes it at most a major-version change and, on inspection, not worth one then either.

If consistency is preferred anyway. Do it as a deliberate major: move the real types into SafeWebCore.Infrastructure and leave obsolete root-namespace shims for one major, with the PublicAPI entries and the backward-compatibility policy updated in the same change.

All five decisions are in the spine now: four became AD-16 to AD-19 and one amended AD-10. The question text and the decisions stay on record in the spine's Open Questions section, and all four rules that needed a code change now say implemented 2026-09-27: both dispatchers, the fail-closed mappings, the version form and the validator guard.

What the reviewer gate changed

  • AD-7 was wrong as drafted. NetSecureHeadersDiagnosticsService kept a second header table of its own. Fixed: response emission lives in one place, the preview is a projection, and AD-8 got step 5 to keep them in lockstep.
  • AD-5 and AD-7 ownership definitions tightened; AD-10 sink ordering stated; AD-12 geo-service wording; AD-13 risk population; AD-14 post-configure additivity; AD-15 added for the analyzer rules.
  • The stack table was corrected on two facts: all five packages are published, and the local RC SDK's support window ends 2026-10-13 while CI builds on 10.0.x.
  • Then the five open questions were decided (2026-09-27): AD-10 amended, AD-16 to AD-19 added. Each of the three reports in reviews/ now carries an addendum recording what its findings turned into.

Where this goes next

  • Adopt the spine as a spec companion (bmad-spec) so downstream work can cite stable AD-n ids.
  • Then stories (bmad-preview-ticketing), or straight to a small change through bmad-build.
  • Landed on 2026-09-27: per-sink isolation and the swallowed-failure counters in both dispatchers, the fail-closed verdict mappings in one shared helper, the AdditionalHeaders guard in the validator, and the FraudDetection move to 1.1.0 with the corrected release documentation.
  • Close the two enforcement gaps — the lockstep test and the architecture test — if the ids are to mean anything to an agent that only runs the build.
