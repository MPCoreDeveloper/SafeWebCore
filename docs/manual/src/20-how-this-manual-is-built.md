# 20. How This Manual Is Built

The chapters you are reading are Markdown files in `docs/manual/src`. The PDF beside them is generated by a console tool in
`tools/SafeWebCore.Manual`, which you can build and run yourself, and no page is typeset by hand. The tool is not packed
with the library: it is a maintainer utility, and it is described here because its output is the book you are holding.

The design is deliberately small, and the reason is the same reason this library exists: a build that has to be
understood is a build that has to be maintained. SafeWebCore has no PDF reader of its own, so this pipeline does not
pretend to have one — it converts, it prints, and it stops.

## The three stages

| Stage | Reads | Writes | Done by |
| --- | --- | --- | --- |
| Markdown to HTML | `docs/manual/src/*.md`, `manual.css` | one HTML document | `MarkdownConverter`, `SyntaxHighlighter`, `ManualHtml` |
| HTML to pages | that document | a printed PDF | Chrome or Edge, headless |
| Check | the printed PDF | a pass/fail line | `PrintResult` over the file's header and size |

Each stage is one file. `--keep-html` leaves the generated HTML on disk so you can open it in a browser and see exactly
what the printer is given; `--no-print` stops after the HTML is written.

## Markdown to HTML

The converter understands the subset the chapters use and refuses nothing — it treats an unknown construct as a
paragraph — because a chapter is written by hand and reviewed as text, not generated:

- ATX headings (`#` to `####`), each with an anchor that is unique in the book;
- fenced code blocks with a language label, highlighted into class names rather than inline colours;
- pipe tables with a header row;
- single-line blockquotes (the `> **Note.**` callouts);
- flat lists, inline code, bold, italic, links and horizontal rules.

Code fences are highlighted into class names — `k` for a keyword, `s` for a string, `c` for a comment, `m` for a number,
`t` for a type name. Those names are what `manual.css` styles, so the same book can be restyled without touching the
converter. C#, shell, PowerShell, JSON and XML have rule sets; any other fence is escaped and printed without colour.

Anchors are made unique across the whole book, not per chapter, because the contents page and the in-document links
address a heading by its anchor; two chapters with a section called "Overview" must not share one.

## The browser lays out, and nothing else

Chrome is started headless with `--print-to-pdf`, a throwaway profile and `--no-pdf-header-footer`:

```powershell
chrome.exe --headless=new --disable-gpu --disable-extensions --no-pdf-header-footer `
  --run-all-compositor-stages-before-draw --virtual-time-budget=20000 `
  --user-data-dir=<temporary profile> --print-to-pdf=docs\SafeWebCore-Manual-1.9.0.pdf `
  file:///<repository>/docs/manual/build/manual.html
```

`manual.css` does the pagination work: A4 with 17 mm side margins, a cover that fills the first page, a contents page, a
page break before every chapter (`h1 { break-before: page }`), tables that repeat their header, and code blocks that do
not split across pages.

## What this build does not do

- **It does not measure pages, so the contents has no page numbers.** The SharpCorePDF manual can add them because that
  library reads PDFs; SafeWebCore cannot, and a made-up number would be worse than none. The contents lists chapters and
  sections, in order, with working internal links.
- **It does not add a running footer or a PDF outline.** Both would need a PDF post-processing pass over the printed
  file — an edit this library has no surface for.
- **It does not check the prose.** The check proves that a PDF was produced — `%PDF-` header, non-trivial size — not that
  the sentence under a heading is true. A chapter that states a wrong default builds happily and prints the wrong number.
- **It does not run in CI.** The tool is compiled with the rest of the solution, but the book is generated on a machine
  with a browser, before a release, and the release records the document it produced.
- **It is not a general Markdown library.** Nothing in it is shaped for another document.

## Running it

```powershell
dotnet run --project .\tools\SafeWebCore.Manual                          # writes docs/SafeWebCore-Manual-<version>.pdf
dotnet run --project .\tools\SafeWebCore.Manual -- --keep-html          # also keeps docs/manual/build/manual.html
dotnet run --project .\tools\SafeWebCore.Manual -- --no-print           # stop after the HTML
```

| Argument | What it changes |
| --- | --- |
| `--root <path>` | the repository root; found from the tool's location when it is not given |
| `--out <path>` | the file to write; `docs/SafeWebCore-Manual-<version>.pdf` by default |
| `--version <x.y.z>` | the edition the cover states; default read from `src/SafeWebCore/SafeWebCore.csproj` |
| `--keep-html` | keep `docs/manual/build/manual.html` |
| `--no-print` | skip the browser and the PDF |

Chrome or Edge is the only prerequisite beyond the .NET SDK. `SAFEWEBCORE_CHROME` points the printer at a browser
installed somewhere else, and the build fails with a message that says so rather than with a stack trace.

The run prints what it did — chapters, headings, the HTML it wrote, the browser it used, the PDF size and a `check` line
that is `ok` only when the written file starts with a PDF header and is larger than a page of text. A build that silently
lost its output cannot be mistaken for a good one.
